# Rosco approved-sender mail

Automatic reading/replies are disabled unless server-side `ROSCO_AUTO_REPLY_ENABLED`, trimmed and lowercased, equals `true`. `ROSCO_APPROVED_SENDERS` is a comma-separated list of complete mailbox addresses, trimmed and lowercased. Never use a `NEXT_PUBLIC_` variable. No addresses or credentials belong in source control.

The signed webhook still only validates, sanitizes, and durably enqueues. Its atomic Lua insertion indexes a new task for automatic processing only when the receipt-time enabled flag is exactly true after normalization and the parsed webhook sender exactly matches the private allowlist. The webhook passes only a boolean candidate flag to storage; it does not store the sender mailbox. Existing review records and owner-only APIs/UI are unchanged. Historical records created before this feature are not automatically indexed. Messages received while disabled or unapproved stay exclusively in owner review, even if configuration changes or webhook deliveries are retried later. The untrusted webhook prefilter never replaces canonical revalidation.

The `CRON_SECRET` bearer-protected `/api/cron/rosco-auto-mail` route claims one due task per invocation. Its minute schedule is Vercel's shortest supported cron interval (requires Pro/Enterprise; Hobby only supports daily schedules). No provider settings are changed by this code.

A two-minute Redis lease and token-fenced writes protect processing. Terminal state is durable, without expiration. Up to four attempts use exponential backoff (two, four, eight minutes) for pre-delivery failures. Expired processing leases recover; expired delivery leases require review. Missing/malformed sender, mismatched canonical identifiers, unaligned authentication, unsafe labels, non-clear Agent Armor results, attachments, missing plain text, or selected plain text over 12,000 UTF-8 bytes become terminal `review_only`. One bare mailbox or one standard display-name/angle-mailbox value is accepted. Only the normalized mailbox authorizes a sender. Controls, nested brackets, address lists, trailing text, ambiguous display names, quoted local parts, and Unicode mailboxes are rejected. Quoted display names may include commas; no text outside the mailbox authorizes a sender.

Only the canonical AgentMail message is trusted for metadata verification; its body remains untrusted user content. At least one acceptable canonical SPF/DKIM/DMARC pass is required. AgentMail reports SPF only when aligned; a missing SPF domain is permitted, while a supplied domain must conservatively equal the From domain or be its subdomain. DKIM requires a named signing domain equal to the From domain or its subdomain, without guessing organizational domains from public suffixes. DMARC requires an exact From-domain match. Domain comparisons ignore case. Unrelated named domains fail closed, and unsafe labels always override passing results. Anthropic receives the bounded canonical email-thread history, including relevant inbound messages and Rosco's prior replies, as untrusted user data under a fixed system policy. The application supplies no tools, repository contents or access, repository or agent-session history, credentials, sender configuration, or internal configuration to the model. The email-thread content itself may contain private information; the fixed policy prohibits disclosing personal data. Generation is limited to 600 tokens and accepted output to 4,000 UTF-8 bytes. Model instructions prohibit disclosure and false claims of completed actions; they cannot guarantee arbitrary model wording. The email path has no action tools.

Before sending, Redis stores delivery intent and generated text. Only the existing message's reply endpoint is used, with plain text, an explicit validated sender recipient (overriding untrusted Reply-To), `reply_all: false`, and a SHA-256 inbox/message-derived idempotency key. Compatible replay success is accepted. Explicit HTTP 408, 425, 429, 500, 502, 503, and 504 responses are retryable using identical saved text and the same idempotency key within one hour, bounded by the four-attempt limit and backoff. All other unsuccessful or ambiguous delivery outcomes, including timeouts and conflicts, require owner review; they are never blindly resent. AgentMail keys expire after 24 hours. Review-only may therefore include a reply already delivered when its acknowledgement was lost. An owner must reconcile AgentMail delivery history before manually replying. Terminal automatic status is in `rosco:auto-mail:v1:states`; the existing review interface continues showing all original review tasks.

Required server environment names: `ROSCO_AUTO_REPLY_ENABLED`, `ROSCO_APPROVED_SENDERS`, `CRON_SECRET`, `AGENTMAIL_API_KEY`, `AGENTMAIL_ROSCO_INBOX_ID`, `ANTHROPIC_API_KEY`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`. Existing webhook configuration still requires `AGENTMAIL_WEBHOOK_SECRET`; existing owner authorization configuration is unchanged.

Before manual activation, review sender entries privately in Doppler, confirm AgentMail read/reply permissions and canonical authentication metadata, confirm the Vercel plan supports the minute cron and its CRON_SECRET bearer, synchronize approved environment configuration, and separately approve deployment and activation. Keep activation disabled until those checks are complete. Do not change AgentMail settings merely to run this feature.

Run focused tests with `node --experimental-strip-types --test scripts/rosco-auto-mail.test.mjs`. The integration test requires local `redis-server` and `redis-cli`; it starts an isolated temporary Unix-socket server with persistence disabled and removes it afterward. No live AgentMail, Anthropic, or production Redis calls are made.

Provider contracts: [canonical metadata](https://docs.agentmail.to/api-reference/inboxes/messages/get), [reply](https://docs.agentmail.to/api-reference/inboxes/messages/reply), [idempotency](https://www.agentmail.to/docs/knowledge-base/preventing-duplicate-sends), [cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing).

## Loop prevention

Loop decisions use only the canonical AgentMail responses, never webhook header hints or model interpretation. [Get Message](https://docs.agentmail.to/api-reference/inboxes/messages/get) documents `headers` as an optional string-to-string map. Header names are compared case-insensitively. A present `Auto-Submitted` value must normalize to exactly `no`; every other value, including empty or malformed values, requires owner review. List indicators, automated-reply indicators, bulk/list/junk/auto-reply precedence, requested automatic-response suppression, malformed header maps, and duplicate case-insensitive header names also require review. Missing headers alone do not reject a human message. Header contents remain sender-controlled suppression signals: they can never authorize a sender or replace canonical authentication.

The processor additionally calls [Get Inbox](https://docs.agentmail.to/api-reference/inboxes/get). Its documented `inbox_id` must match the stored reference, and its documented `email` must parse as one mailbox. A deactivated inbox or invalid/missing identity requires review. A sender equal to that canonical inbox email is suppressed even when allowlisted; untrusted message `To`, `Reply-To`, display names, and configuration guesses are not inbox identity. The canonical message's `thread_id` must also match the stored task.

**Policy: one thread is the conversation source of truth, with successive human replies.** Each new approved, authenticated, eligible human message may receive one automatic reply within the same provider thread. There is no permanent one-message restriction. A durable Redis thread lease serializes history collection, generation, and delivery across workers, in addition to the existing per-message lease. Both token and deadline are checked before generation and atomically before saving delivery intent or success. Thread ownership is held across retry backoff so later messages cannot generate competing replies while the prior message awaits delivery. Expired predecessors are recovered first; stale workers cannot save delivery intent. A busy worker defers without consuming a transient-failure attempt. Canonical target timestamps older than 15 minutes (or more than five minutes into the future) require review, limiting stale backlog processing.

Each inbox/thread has rolling limits of **3 reply allowances per 10 minutes and 12 per 24 hours**. Allowances are reserved atomically on first eligible admission, so parallel workers cannot overrun them; retries of that same message reuse its allowance. A failed history check or generation can consume an allowance even without a send, intentionally bounding model usage and attempted replies. A rate violation opens a **30-minute circuit breaker**. Three consecutive admitted messages ending unsuccessfully also open it for 30 minutes; a confirmed success resets the failure count. New messages during the open period go directly to owner review and do not extend the breaker. Already-admitted delivery retries keep their allowance and can finish under the existing retry bounds. Rate-rejected messages are terminal review-only rather than delayed for a later catch-up burst. Rolling allowances age out, and newly received eligible human messages can resume when both breaker and rolling limits permit. These limits allow ordinary paced follow-ups while bounding accidental responder loops. Separate inboxes and threads have separate leases, counters, breakers, and reply checkpoints. This is not a global inbox spending limit.

[Get Thread](https://docs.agentmail.to/api-reference/inboxes/threads/get) documents inbox-scoped thread retrieval with `limit` and `page_token`. Its first page holds the newest messages in ascending timestamp order; `next_page_token` retrieves older pages. The processor follows up to three pages of ten messages, then builds a complete chronological transcript including relevant inbound plain text and Rosco's previous outbound plain-text replies. A successful reply's provider message ID is persisted as the next worker's required history checkpoint. The transcript must include the current target and that checkpoint. All history, including previous replies, is sent as **untrusted user data under the fixed system policy**, never as system/developer instructions or privileged assistant messages. Historical inbound senders must still be approved and authenticated; unsafe or automated inbound history requires review instead of disclosing it to the model.

History is bounded to **30 messages, 24,000 selected plain-text UTF-8 bytes, 32,000 serialized context bytes, and 256,000 raw response bytes across pages**. Generation remains limited to 600 tokens and accepted replies to 4,000 bytes. Missing pages, repeated pagination tokens, changed snapshots, count mismatches, missing known replies, duplicate IDs, wrong inbox/thread references, unusable or oversized text, and attachment-bearing history explicitly require owner review. No truncated history, invented summary, or silently omitted message is presented as the entire conversation. Long threads exceeding these bounds therefore require owner review; automatic summarization is not implemented. Provider/network fetch failures remain bounded retryable failures. Saved-text delivery retries reuse their original context result and identical payload/key rather than regenerating against changed history. A stored SHA-256 fingerprint covers rendered text, normalized recipient, and outbound automatic-response headers; any change requires review before POST. Legacy saved text without that fingerprint also requires reconciliation. No approved mailbox value is stored for this fingerprint.

[Reply To Message](https://docs.agentmail.to/api-reference/inboxes/messages/reply) supports a custom `headers` map in the request body. Automatic replies now include `Auto-Submitted: auto-replied` and `X-Auto-Response-Suppress: All`, alongside the existing explicit recipient, plain text, no reply-all, and deterministic HTTP idempotency key. These headers request cooperation from other responders; the durable local thread lease, rolling limits, and circuit breaker provide independent protection.

Before production use, verify permission to read the canonical inbox as well as messages, actual provider thread stability and header preservation, and durable Redis lease/rate/breaker behavior. Existing pre-repair sends are not reconstructed into counters or reply checkpoints. Reconcile old threads and outstanding delivery intents before any separately approved activation. A retry created by an older deployment may conflict with the new outbound headers under the same idempotency key; conflicts remain review-only. No deployment, provider configuration, queue clearing, or production activation is authorized by this documentation.

## Development setup and validation

The repository's `compose.yaml` builds the `development` target of the Node 22 Bookworm `Dockerfile`. That target includes `redis-server` and `redis-tools`, providing the server and CLI required by the real Redis tests. These packages are development-only. No additional Compose service, TCP port, volume, production dependency, or runtime Redis connection is needed: tests start a disposable Unix-socket Redis server with persistence disabled. Do not point these tests at production Redis.

When setting up the workspace or changing development-image dependencies, build and recreate only the existing David Compose project's `web` service. Preserve its actual project name, all Compose override files (including governance mounts), bind mounts, and named volumes. Run validation inside that development container from `/app`. Rebuilds and restarts are operator-controlled development actions; they do not authorize production deployment, provider changes, or mail activation.

The shared fixture in `scripts/lib/redis-test-server.mjs` reports missing tooling, failed spawn, early process exit, and readiness timeout as explicit failures. Cleanup observes process closure from startup, avoids waiting for an exit event that cannot occur after failed spawn, bounds graceful shutdown, escalates to forced shutdown when necessary, and removes its temporary directory even on startup failure. Missing Redis coverage is a failing check, never a silent skip. Harness regression tests use short-lived local Node processes and require no Redis installation.

Run all four suites sequentially from the repository root inside the development container:

```sh
npm run test:agentmail
node --test scripts/rosco-auto-mail.test.mjs
node --test scripts/redis-test-server.test.mjs
node --test scripts/rosco-mail-history.test.mjs
```

A passing harness suite or passing non-Redis assertions does not establish that the full mail suite passed. The real Redis tests must execute to verify Lua claims, lease fencing, thread serialization, rate limits, circuit recovery, concurrent new message IDs, and delivery retries.
